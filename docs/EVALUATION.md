# Evaluation on planted errors

The evaluation harness ports the archived building-hall benchmark and adds a precast suite derived from the repository's LV 11 fixture. It plants known defects in clean synthetic bills, writes both GAEB X83 and JSON, parses every output using the normal importer or adapter, and checks that the parsed inputs contain the intended changes. The presenter can upload the same [demo files](../data/demo/README.md).

## Reproduce the results

Run from the repository root with the backend and importer dependencies installed.

```sh
export PYTHONPATH=backend:backend/importer
python -m analysis.eval mutate
python -m analysis.eval run
python -m analysis.eval report --format md --write eval_out/report.md
python -m analysis.eval fp
python -m pytest -q backend/analysis/tests
```

Use `--backend x83` on the report to reproduce the per-file counts for one format. The default builds both suites with mutator seed 1 and three examples per eligible building-hall mutation. `--only QTY,L2-REMOVE` selects building-hall mutations by prefix. Use a fresh `--out` directory for a different selection. The precast seed is regenerated by `python -m analysis.eval.seeds.make_precast_lv11`. To regenerate the presenter files, copy the two X83 files from `eval_out/demo/` to `data/demo/` after the default mutation run.

The optional `run --layers 1,2,3` uses the configured provider from the existing analysis pipeline. The evaluation command checks the included synthetic seed checksum and the generated files' checksums before sending excerpts to a model. Real-file labelling runs Layers 1 and 2. Provider setup and credentials stay in the environment. For a deterministic check of unavailable-layer scoring use `ANALYSIS_L3_PROVIDER=none python -m analysis.eval run --layers 1,2,3`.

## Snapshot at Task 05

These figures describe the labelled fixtures with Layers 1 and 2 on the task's main baseline. X83 and JSON produced the same planted-label outcomes. The figures exclude the combined presenter files from recall and rule precision.

| Suite per format | Caught | Missed | Known gaps | Layer not run |
| --- | ---: | ---: | ---: | ---: |
| Building hall | 76 | 0 | 13 | 0 |
| Precast LV 11 | 1 | 5 | 0 | 2 |

- The building hall matched the archived result of 76/76 for cases with a supporting rule. The 13 known gaps remain represented in overall recall.
- The precast billing-unit conflict is detected by the existing rule. The five misses cover the planned strength, layer sum, placeholder, description conflict, and workshop drawing checks. The two Layer 3 cases cover missing specifications and ambiguous rebar scope.
- Both clean seeds and all harmless controls produced zero findings. The default replay checks 46 controls across both formats, including the underlying clean seeds.
- The generated report includes recall by mutation, precision by rule, individual cases, and expected consequences such as changes in subtotals. A finding counts as a catch when its rule and affected position or scope match a label.

The local browser upload shows the building-hall zero quantity, duplicate and missing edge insulation, and the precast billing-unit conflict. On this baseline the X83 upload check omits the source line amount. The CLI report verifies the planted arithmetic and its subtotal consequences.

Each generated file has a `construct-eval-labels/1` sidecar with stable position codes, the expected or acceptable rule IDs, and a link to its clean baseline. A run subtracts findings already present in the corresponding baseline. This keeps synthetic measurements tied to the planted faults. The `fp` run checks the controls directly, including their clean baselines.

## Preliminary review of repository files

The [real-file labels](../backend/analysis/eval/labels/real_findings.csv) cover the existing warning and error groups in the seven repository X83, D83 and D86 files. Four files had no warning or error groups on this baseline. Among the nine labelled groups, one is a confirmed source error, one is a false alarm, three are consequences of an importer interpretation, and four still need supporting project evidence. The labels describe groups of existing findings. They measure neither missed real errors nor production recall.

For example, the two duplicate disposal surcharges in the 501-24-01 source each refer to a distinct preceding root-stock position. In StBALV23040, the malformed `TEL00009` key accounts for the missing €982.20 in two nested subtotals. The source identifies the malformed key and amount, and the correct position number still needs review.

To prepare another group-level review:

```sh
python -m analysis.eval label-template 'data/tenders/StBALV23040.D86'
```

Use `true_error`, `false_alarm`, `importer_artefact`, or `unsure`. A wildcard finding ID applies a verdict to a whole file-and-rule group. Verify the affected records before replacing an unsure verdict. Independently labelled project cases are still needed for production accuracy and clause-level DIN claims.
